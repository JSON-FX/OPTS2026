# EDTS 2027 MIS staging

This package targets only `https://staging.opts.lguquezon.local`, with staging SSO and staging Connect. It uses the accepted SSO baseline plus widget source. It does not include the primary checkout's uncommitted UI changes. No production target or deployment trigger is added.

## Operator preparation

1. Publish and merge the reviewed source. `mis-edts-image.yml` tests PHP, frontend, and deployment scripts, then builds one linux/amd64 image. Only successful main pushes publish `mis-image-<full-sha>` containing the image archive and checksum. Retain existing workflow checks. Add `JSON-FX/OPTS2026` to the MIS read-only token repository allowlist if missing; never put that token in CI.
2. Install this package as operator-owned `/srv/mis-deployment/edts/staging`, directory mode700. Copy `runtime.env.example` and `mysql.env.example` to private `.env` files named `runtime.env` and `mysql.env`. Generate fresh app/DB/Reverb/widget secrets privately. The DB user/password must match between files. Create `secrets/mysql-root-password` with a separate password. Keep secrets out of Git and shell arguments. The directory must be inaccessible to application containers.
3. Copy only the public office root certificate to `office-ca.crt`. The app trusts it through the read-only `office-ca.ini` mount. No localhost/Mac/host-gateway overrides belong here. Confirm Windows DNS resolves staging EDTS, SSO, and Connect normally. Issue the exact EDTS hostname certificate and review `proxy.conf.example` against the installed proxy paths.
4. Register a distinct staging EDTS confidential SSO client with callback `https://staging.opts.lguquezon.local/auth/sso/callback`. Enable directory access and grant only approved synthetic staging users. Provision its measured request budget; the widget rollout guide documents why the old100/minute allowance can throttle even two users. Do not copy local accounts or secrets.
5. Register the staging EDTS host/key in staging Connect: parent origin `https://staging.opts.lguquezon.local`, introspection `https://staging.opts.lguquezon.local/connect/pilot/introspect`. Add that exact frame ancestor to Connect ingress while preserving other approved hosts. Enable `CONNECT_PILOT_ENABLED` only after both registrations and credentials are ready.
6. Set `TRUSTED_PROXIES` to the proxy's exact staging-ingress address/CIDR, not `*`. The package uses its own host-only `edts_staging_session` cookie, encrypted database sessions, database cache/queue, storage volume and MySQL. MAIL_MAILER is log. No production volume or database is referenced.
7. Install `registration.json` initially at `/etc/mis-deployment/edts/staging/registration.json`, outside the timer-scanned apps directory. Its `schema_compatible` declaration applies to the reviewed additive migrations and fresh staging setup only; inspect future migrations before retaining it. Make scripts operator-owned. The first manual MIS stage run writes `image.env` with the verified image; it contains only APP_IMAGE. After staging acceptance, an operator may copy registration into `/etc/mis-deployment/apps/edts.json` to enable automatic staging updates.
8. Before the first app deployment, provision this package's MySQL using `APP_IMAGE=mis-edts:not-selected docker compose --project-name mis-staging-edts -f compose.yml up -d mysql` and wait for healthy. The placeholder only resolves Compose while starting MySQL; never start the app with it or persist it in image.env. The helper intentionally uses `--no-deps` for application services. Never substitute production MySQL. Fresh data is required for first onboarding; no production import is authorized.

## Deployment sequence

The MIS helper verifies and loads the current-main artifact, writes image.env, starts the app image, invokes migrate.sh, then waits for health and runs smoke.sh. APP_AUTO_MIGRATE and APP_AUTO_SEED are false in MIS. Local Compose retains its existing automatic startup defaults.

The migration hook runs `migrate --force` and the staging-only `StagingReferenceSeeder`. Bootstrap is idempotent, adds three roles, three fund types and action labels, and preserves existing reference edits. It adds no suppliers, particulars, users, or offices. SSO provisions users and synchronizes offices; operators configure workflows explicitly. CI loads the candidate image and runs `test-image.sh`: fresh pinned MySQL migration, repeated reference bootstrap, clean reference counts, Nginx validation, startup/login health, Reverb reachability, and callback query log redaction under a forced PHP-FPM failure before artifact upload. The temporary container/network/data are removed on exit. Do not run migrate:fresh or DatabaseSeeder in MIS.

The same application image is portable: Blade renders only the public Reverb key plus current APP_URL host/scheme/port at runtime. Private Reverb/SSO/widget secrets are never emitted. The internal broadcast connection remains localhost:6001; the office proxy exposes browser WebSocket traffic on the staging hostname. No Vite host/key build arguments are needed for future production promotion.

Readiness checks validate staging environment/origins, enabled widget configuration, reference roles, database, SSO directory transport, trusted Connect health and external login/up. They are read-only and do not certify a complete user flow. Parent acceptance must additionally verify normal DNS/TLS, SSO login/logout, two-user widget messaging/seen/unread/group behavior, revoked grants, host logout isolation, capacity, queue/scheduler/Reverb, and immutable running image identity. Keep the current Connect capacity issue and concurrent-load gate visible.

## Recovery and isolation

Capture production container/image/volume/network evidence before and after onboarding. No production migrations or synthetic records are permitted. The first deployment has no prior EDTS image: a failed initial install is held for diagnosis; preserve data and logs. Subsequent image rollback never undoes migrations. Keep stage DB/storage backups before changes; test recovery independently. Disable the widget and its Connect host/key if needed without changing independent Connect web access. Retain the revocation table and encryption settings.

The timer registration has staging only. Production needs the exact accepted artifact, separate configuration/SSO/key/data, backup/restore evidence and explicit approval; do not let the staging timer promote it.
